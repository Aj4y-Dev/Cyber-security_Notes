
# Hyper Text Transfer Protocol (HTTP)

Most internet communications are made with web requests through the HTTP protocol. The term `hypertext` stands for text containing links to other resources and text that the readers can easily interpret. The default port for HTTP communication is port `80`. 

## URL

A URL (Uniform Resource Locator) is made of multiple parts.  
Each part has a specific purpose when a client (browser) requests a resource.

```
# structure of URL

http://admin:password@inlanefreight.com:80/dashboard.php?login=true#status
```

| **Component**            | **Example**           | **Description**                                                                                                                      |
| ------------------------ | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **Scheme**               | `http://`, `https://` | Identifies the protocol used. Always ends with `://`. Examples: HTTP, HTTPS.                                                         |
| **User Info** (Optional) | `admin:password@`     | Contains username and password for authentication. Placed before the host and ends with `@`. Rarely used today for security reasons. |
| **Host**                 | `inlanefreight.com`   | The address of the resource. Can be a domain or an IP address.                                                                       |
| **Port**                 | `:80`                 | The port number used for communication. Defaults: HTTP → 80, HTTPS → 443. Separated from the host by `:`.                            |
| **Path**                 | `/dashboard.php`      | Specifies the file or directory being accessed. If missing, the server returns a default page (e.g., `index.html`).                  |
| **Query String**         | `?login=true`         | Starts with `?`. Contains key-value pairs sent to the server. Multiple parameters separated by `&`.                                  |
| **Fragment**             | `#status`             | Used by the browser to jump to a section of the page. Not sent to the server.                                                        |

## cURL

cURL is a command-line tool that allows you to send various web requests, automate tasks, and interact with web servers—making it essential for penetration testing and scripting.

### Why Pentesters Use cURL

- Test authentication
- Send custom headers
- Manipulate cookies
- Replay intercepted requests
- Send payloads (XSS, SQLi, LFI, etc.)
- Detect server behavior
- Automate brute-force or enumeration scripts

Below are the most important and frequently used flags:

1.  -X  (Specify HTTP Method)

```
Send a custom HTTP request method.

curl -X POST https://example.com

If we don’t specify -X, cURL uses GET by default.
```

2. -d (Send Data in the Request Body)

```
Used mostly for **POST**, **PUT**, or **PATCH** requests.

curl -X POST -d "username=admin&password=123" https://example.com/login

Automatically sets Content-Type: application/x-www-form-urlencoded.
```

3.  -H (Add Custom Header)

```
Useful for: Cookies,Tokens,User agents,Content-Type

curl -H "User-Agent: pentester" https://example.com
```

4.  -v (Verbose Output)

```
Shows all details: Sent request, Response headers, Status codes

curl -v https://example.com
```

5. -o (Save Output to a File)

```
curl -o page.php https://example.com/dashboard.php (small o)

curl -O https://example.com/dashboard.php (big O)
```

6.  --cookie (Send Cookies)

```
curl --cookie "session=abcd1234" https://target.com
```

7.  -s (Silent Mode)

```
curl -s https://example.com

example: Silently fetch a page and pipe it

curl -s https://example.com | grep "admin"
```

# Hypertext Transfer Protocol Secure (HTTPS)

The main drawbacks of HTTP is that all data is transferred in clear-text. This means that anyone between the source and destination can perform a Man-in-the-middle (MiTM) attack to view the transferred data. HTTPS (HTTP Secure) protocol was created, in which all communications are transferred in an encrypted format, so even if a third party does intercept the request, they would not be able to extract the data out of it.

NOTE: In HTTPS, the content is encrypted, but DNS queries can still reveal which server you are connecting to. Using an encrypted DNS provider or a VPN helps ensure that both DNS queries and the connection are protected from interception.

## HTTPS Flow

![[Pasted image 20251202154538.png]]


When you type **http://** instead of **https://**, the browser first sends an **unencrypted HTTP request** to **port 80**.  The server sees this and replies with a **301 redirect**, telling the browser to switch to **HTTPS on port 443**. 

### **SSL/TLS Key Exchange – Functional Summary**

1. **Client Hello:** Browser sends supported TLS versions, cipher suites, and a random number.
2. **Server Hello & Certificate:** Server chooses TLS/cipher, sends its certificate with public key.
3. **Client Verification & Premaster Secret:** Browser verifies certificate, generates a premaster secret, encrypts it with server’s public key, and sends it.
4. **Server Decryption:** Server decrypts premaster secret using its private key.
5. **Session Key Generation:** Both sides use client random, server random, and premaster secret to derive the **shared symmetric session key**.
6. **Secure Communication:** All further data is encrypted with this session key.

NOTE: 
- An **HTTP downgrade attack** happens when an attacker forces a secure HTTPS connection to use **unencrypted HTTP** instead.
- This is typically done by setting up a **Man-In-The-Middle (MITM) proxy**, which intercepts all traffic between the client and the server without the user knowing.
- Once the connection is downgraded, any data sent is in **clear text** and can be read or modified by the attacker.
- **Modern protections:** Most current browsers, servers, and web applications have built-in measures to **prevent downgrade attacks** and ensure secure communication.

## cURL for HTTPS

**cURL** automatically handles **HTTPS communication**, including the **TLS handshake**, and encrypts/decrypts data for secure transfer. By default, cURL **verifies SSL certificates** to ensure the server is trusted. If a website presents an **invalid or outdated SSL certificate**, cURL **will not continue the connection**. This behavior protects against **Man-In-The-Middle (MITM) attacks** and ensures data confidentiality and integrity.


# HTTP Requests and Responses

**HTTP communication operates on a request–response model.** An HTTP request is initiated by a client, such as a web browser or command-line tool (e.g., cURL), and is processed by a server, typically a web server. The request includes essential details such as the target resource (URL, path, and parameters), request data, headers, and additional configuration options. Upon receiving and processing the request, the server returns an HTTP response, which contains a status code indicating the outcome of the request and may include the requested resource data if the client is authorized to access it.

### HTTP Request (Client → Server)

```
POST /login HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0
Content-Type: application/x-www-form-urlencoded
Content-Length: 29

username=admin&password=1234
```
### Explanation

- `POST /login HTTP/1.1` → Client requests the `/login` resource using POST
- `Host` → Target server
- `User-Agent` → Client software (browser)
- `Content-Type` → Format of sent data
- `Content-Length` → Size of request body
- **Body** → Login credentials sent to the server

### HTTP Response (Server → Client)

```
HTTP/1.1 200 OK
Date: Fri, 27 Dec 2025 10:30:00 GMT
Server: Apache/2.4.57
Content-Type: text/html
Content-Length: 1250

<html>
  <body>
    <h1>Welcome, admin!</h1>
  </body>
</html>
```

### Explanation

- `200 OK` → Request processed successfully
- `Server` → Web server software
- `Content-Type` → Response data type
- **Body** → HTML content returned to the client

#  HTTP Headers

HTTP headers are used to **exchange metadata and control information** between the client and the server during HTTP communication. These headers provide instructions and contextual details about the request or response. Some headers are specific to requests or responses, while others are shared across both. 

Each HTTP header consists of a **header name** followed by one or more **values**, separated by a colon (`:`). Based on their purpose and usage, HTTP headers can be classified into the following categories.

1. General Headers:

	General headers apply to **both HTTP requests and responses** and are used to convey information about the message itself rather than the content.

```
Date: Tue, 26 Dec 2025 10:30:00 GMT
Connection: keep-alive
```

- `Date`: Specifies the date and time the message was sent
- `Connection`: Controls connection behavior (e.g., keep-alive)

2. Entity Headers:

	Entity headers describe the **content (entity)** being transferred in the HTTP message. They may appear in **both requests and responses**, but are most commonly found in **responses** and **POST/PUT requests**.

|Header|Example|Description|
|---|---|---|
|**Content-Type**|`Content-Type: text/html; charset=UTF-8`|Specifies the media type of the resource being transferred. The charset defines the encoding standard.|
|**Media-Type**|`Media-Type: application/pdf`|Similar to Content-Type; describes the format of the transmitted data and influences how the server interprets input.|
|**Boundary**|`boundary="b4e4fbd93540"`|Separates multiple entities within a single message, commonly used in multipart form data.|
|**Content-Length**|`Content-Length: 385`|Indicates the size of the message body in bytes. Required for the server to correctly read request data.|
|**Content-Encoding**|`Content-Encoding: gzip`|Specifies the encoding or compression applied to the content before transmission.|
3. Request Headers:

	Request headers are sent **only by the client** and provide additional information about the request, the client environment, and preferred response formats. These headers do not describe the message body.

|Header|Example|Description|
|---|---|---|
|**Host**|`Host: www.inlanefreight.com`|Identifies the target host. Essential for virtual hosting and an important enumeration target in security testing.|
|**User-Agent**|`User-Agent: curl/7.77.0`|Identifies the client software, browser type, version, and operating system.|
|**Referer**|`Referer: http://www.inlanefreight.com/`|Indicates the source of the request. This header can be manipulated and should not be trusted for security decisions.|
|**Accept**|`Accept: */*`|Specifies the media types the client can process.|
|**Cookie**|`Cookie: PHPSESSID=b4e4fbd93540`|Sends stored cookies for client identification, session management, and preference tracking.|
|**Authorization**|`Authorization: Basic cGFzc3dvcmQK`|Used for authentication. Tokens or credentials are sent to verify client identity.|
4. Response Headers:

	Response headers are sent **only by the server** and provide metadata about the response, server behavior, and authentication requirements.

|Header|Example|Description|
|---|---|---|
|**Server**|`Server: Apache/2.2.14 (Win32)`|Reveals information about the web server software and version.|
|**Set-Cookie**|`Set-Cookie: PHPSESSID=b4e4fbd93540`|Sends cookies to the client, which are stored for future requests.|
|**WWW-Authenticate**|`WWW-Authenticate: Basic realm="localhost"`|Indicates the authentication method required to access the resource.|
5. Security Headers:

	Security headers are a specialized class of **response headers** designed to enhance browser-side security by enforcing policies that mitigate common web attacks.

|Header|Example|Description|
|---|---|---|
|**Content-Security-Policy (CSP)**|`Content-Security-Policy: script-src 'self'`|Restricts loading of external resources and mitigates XSS attacks.|
|**Strict-Transport-Security (HSTS)**|`Strict-Transport-Security: max-age=31536000`|Forces HTTPS usage and prevents protocol downgrade attacks.|
|**Referrer-Policy**|`Referrer-Policy: origin`|Controls whether and how the Referer header is included in requests.|
### Browser Developer Tools

Browser Developer Tools provide a practical interface for inspecting HTTP requests and responses, allowing detailed analysis of headers, payloads, and status codes directly within the browser environment.

# HTTP Methods and Codes

The HTTP protocol defines multiple **request methods** that specify how a client interacts with a resource on a server. These methods inform the server **how to process the request** and what type of response should be returned. In addition, **HTTP status codes** are included in server responses to indicate the outcome of processing a client’s request.

HTTP methods can be observed directly in HTTP requests. For example, when using **cURL** with the `-v` option, the method appears in the request line (e.g., `GET / HTTP/1.1`). Similarly, in **browser Developer Tools**, the HTTP method is displayed in the _Method_ column of the Network tab. The server’s response includes a **status code** that reflects the result of the request.

### HTTP Request Methods

HTTP request methods define the **action** to be performed on the target resource. Some of the most commonly used methods are described below.

|Method|Description|
|---|---|
|**GET**|Requests a specific resource from the server. Additional parameters may be passed using query strings in the URL (e.g., `?param=value`).|
|**POST**|Sends data to the server in the request body. Commonly used for form submissions, authentication, and file uploads. Supports various data formats, including text and binary data.|
|**HEAD**|Similar to GET, but retrieves only the response headers without the message body. Often used to check metadata such as content length.|
|**PUT**|Creates or replaces a resource on the server. If not properly restricted, it can allow unauthorized file uploads.|
|**DELETE**|Removes an existing resource from the server. Improper access control may result in denial-of-service conditions.|
|**OPTIONS**|Returns information about the communication options supported by the server, including allowed HTTP methods.|
|**PATCH**|Applies partial modifications to an existing resource without replacing it entirely.|
**Note:** Most traditional web applications primarily rely on **GET** and **POST** methods. However, applications exposing **RESTful APIs** commonly use **PUT**, **PATCH**, and **DELETE** for updating and removing resources.

### HTTP Status Codes

HTTP status codes are returned by the server to indicate the **result of a client’s request**. These codes are grouped into five classes based on their purpose.

|Class|Description|
|---|---|
|**1xx**|Informational responses that indicate request receipt and continuation.|
|**2xx**|Success responses indicating the request was processed correctly.|
|**3xx**|Redirection responses requiring additional client action.|
|**4xx**|Client-side errors caused by invalid or unauthorized requests.|
|**5xx**|Server-side errors indicating failure to process a valid request.|
### Common HTTP Status Codes

| Code                          | Description                                                                          |
| ----------------------------- | ------------------------------------------------------------------------------------ |
| **200 OK**                    | The request was successful, and the response body contains the requested resource.   |
| **302 Found**                 | The client is redirected to another URL, often used after successful authentication. |
| **400 Bad Request**           | The server cannot process the request due to malformed syntax or invalid input.      |
| **403 Forbidden**             | Access to the requested resource is denied, even if the request is valid.            |
| **404 Not Found**             | The requested resource does not exist on the server.                                 |
| **500 Internal Server Error** | The server encountered an error while processing the request.                        |
